# BlazorWasmDotNet8AspNetCoreHosted

## Огляд

Це рішення демонструє повноцінну систему планування модулів: клієнт на Blazor WebAssembly (`Client`), серверне ASP.NET Core API (`Server`) та спільну бібліотеку DTO (`Shared`). Цільова платформа — .NET 8. Для зберігання даних використовується MySQL 8.0.13 або новіший із провайдером Pomelo.EntityFrameworkCore.MySql. У середовищі розробки доступний Swagger для дослідження API.

## Структура рішення

- `BlazorWasmDotNet8AspNetCoreHosted.Client` — вебклієнт Blazor WASM, Razor-компоненти та клієнтські сервіси.
- `BlazorWasmDotNet8AspNetCoreHosted.Server` — ASP.NET Core хост, контролери, DI-налаштування, контекст EF Core та міграції.
- `BlazorWasmDotNet8AspNetCoreHosted.Shared` — спільні DTO й контракти, що використовуються клієнтом і сервером.
- `database-setup.md` для детального налаштування бази даних.

## Безпека виробничого розгортання

Серверний API поки не має автентифікації та рольової авторизації. До інтеграції з університетським SSO/JWT не публікуйте застосунок у відкриту мережу: обмежте доступ приватною мережею, VPN або захищеним reverse proxy. Перед повноцінним запуском потрібно окремо визначити ролі щонайменше для перегляду, укладання розкладу, публікації та адміністрування довідників.

Для оркестратора доступні перевірки `GET /health/live` та `GET /health/ready`. Readiness повертає `503`, якщо база недоступна, початковий сидинг не завершився, залишилися незастосовані міграції або відсутні обов'язкові індекси цілісності.

Якщо TLS завершується на reverse proxy, передайте його точну IP-адресу через `ReverseProxy__KnownProxies__0` (наступні адреси — з індексами `__1`, `__2` тощо). Сервер приймає `X-Forwarded-For`/`X-Forwarded-Proto` лише від цих довірених адрес; не вмикайте глобальну довіру до forwarded-заголовків.

## Попередні вимоги

- Встановлений .NET SDK 8.0.100 або новіший (`dotnet --list-sdks`).
- Локальні .NET-інструменти репозиторію: після клонування виконайте `dotnet tool restore`.
- Доступ до локального екземпляра MySQL 8.0.13 або новішого (або сумісного керованого сервісу). Цей мінімум потрібен для функціональних унікальних індексів конфігурації.
- Node.js/npm знадобиться лише за умови зміни фронтенд-інструментів; для запуску поточного рішення не є обов’язковим.

## Швидкий старт

1. Клонуйте репозиторій.
2. Перевірте, що рішення коректно збирається:
   ```
   dotnet build BlazorWasmDotNet8AspNetCoreHosted.Server.sln
   ```
3. Налаштуйте рядок підключення до бази даних (розділ нижче).
4. Застосуйте міграції:
   ```
   dotnet tool restore
   dotnet ef database update --project BlazorWasmDotNet8AspNetCoreHosted.Server
   ```
5. Запустіть серверну частину:
   ```
   dotnet run --project BlazorWasmDotNet8AspNetCoreHosted.Server
   ```

## Налаштування бази даних

Реальні облікові дані навмисно не зберігаються в репозиторії. Перед запуском підставте валідний рядок підключення, скориставшись одним із способів:

- **Secret Manager (рекомендований локально):**
  ```
  dotnet user-secrets set "ConnectionStrings:Default" "Server=localhost;Port=3306;Database=schedule_db;User=schedule_user;Password=YOUR_PASSWORD;CharSet=utf8mb4;TreatTinyAsBoolean=true;AllowPublicKeyRetrieval=True;SslMode=None" --project BlazorWasmDotNet8AspNetCoreHosted.Server/BlazorWasmDotNet8AspNetCoreHosted.Server.csproj
  ```
- **Змінна середовища:**
  ```powershell
  $env:ConnectionStrings__Default = "Server=localhost;Port=3306;Database=schedule_db;User=schedule_user;Password=YOUR_PASSWORD;CharSet=utf8mb4;TreatTinyAsBoolean=true;AllowPublicKeyRetrieval=True;SslMode=None"
  ```

Детальні покрокові інструкції зосереджені у `database-setup.md`.

> **Застереження:** наявні міграції створюють лише структуру таблиць. Під час запуску сервера автоматично додаються лише базові типи занять (BREAK, CANCELED, RESCHEDULED, EXAM, CREDIT, NONE). Інші довідники або демонстраційні значення потрібно наповнювати окремо.

## Робота з Entity Framework Core

- Якщо команда `dotnet ef` недоступна, відновіть локальні інструменти: `dotnet tool restore`.
- Додати міграцію:
  ```
  dotnet ef migrations add <MigrationName> --project BlazorWasmDotNet8AspNetCoreHosted.Server
  ```
- Оновити базу даних:
  ```
  dotnet ef database update --project BlazorWasmDotNet8AspNetCoreHosted.Server
  ```
- Скасувати останню міграцію (якщо вона ще не застосована до бази):
  ```
  dotnet ef migrations remove --project BlazorWasmDotNet8AspNetCoreHosted.Server
  ```

Design-time фабрика `DesignTimeDbContextFactory` зчитує `ConnectionStrings:Default` із шарів конфігурації (`appsettings*.json`, Secret Manager, змінні середовища). Перед запуском інструментів EF переконайтеся, що рядок доступний.

## Запуск окремих проєктів

- **Сервер:** `dotnet run --project BlazorWasmDotNet8AspNetCoreHosted.Server`
- **Клієнт:** хоститься сервером, тому додатковий запуск не потрібен.
- **Публікація:** `dotnet publish BlazorWasmDotNet8AspNetCoreHosted.Server -c Release`

## Усунення несправностей

- **`Unable to connect to any of the specified MySQL hosts`** — перевірте, чи запущено MySQL та чи правильні хост і порт у рядку підключення.
- **`Рядок підключення 'ConnectionStrings:Default' не налаштовано`** — додайте рядок через Secret Manager, змінні середовища або локальний конфіг перед запуском EF чи сервера.
- **CORS або 404 для API** — впевніться, що сервер активний, а клієнт звертається до актуального базового URL.

## Поточні примітки щодо автогенерації

- Автогенерація розкладу працює через чернетки викладачів і підтримує preflight-перевірку, soft fill, repair-pass, перевірку переходів між корпусами, контроль аудиторій, викладачів і перетинів.
- Перед першим запуском нового семестру для кожного курсу обов'язково задайте **початок поточного навчального періоду** в `/admin/courses`. Міграція залишає поле nullable лише для сумісного розгортання, але UI та job API fail-closed блокують нову генерацію, доки дата не налаштована або якщо діапазон починається раніше за неї. Заняття попередніх періодів після цього не витрачають години, теми й баланс навантаження нового періоду.
- Стан довгих запусків автогенерації зберігається в таблиці `AutoGenJobRuns`: параметри й hash запиту, власник/спроба, lease, статус, прогрес, результат, звіт, помилка та часові мітки. Після оновлення потрібно застосувати міграції.
- Міграцію ownership/lease не можна застосовувати як rolling-оновлення поверх старих серверів, що ще виконують автогенерацію. Спочатку зупиніть приймання нових запусків, дочекайтеся завершення або скасування всіх активних job, зупиніть усі старі instance, зробіть резервну копію БД, застосуйте міграцію і лише після цього запускайте нову версію. Нова версія fail-closed блокує створення job, якщо в БД залишився активний legacy-запис без owner/attempt/lease.
- Усі запуски виконуються через job API `POST /api/teacher-drafts/autogen/jobs`; застарілі синхронні маршрути повертають `410 Gone`, щоб їх не можна було використати в обхід лімітів і черги. Запити `Generate` і `Fill` тепер приймаються лише з `previewOnly: true`; старий прямий запис повертає `400 Bad Request`, тому клієнт і сервер потрібно розгортати узгоджено.
- `Generate` і `Fill` створюють точний незмінний preview-план, який окремо застосовується або відкочується через `/api/teacher-drafts/autogen/jobs/{jobId}/apply` і `/rollback`. Перед зміною БД сервер повторно перевіряє версію плану, ревізії чернеток, релевантну конфігурацію та hard rules. Preview чинний 24 години, безпечний відкіт після застосування — 7 днів; прострочені плани очищуються після 30-денного діагностичного періоду. Для відновлення кнопки відкоту після перезавантаження використовується `/api/teacher-drafts/autogen/plans/latest-rollbackable`.
- Для довгих діапазонів використовуйте фоновий job API/UI, а не короткий синхронний запуск. Незавершене завдання не поновлюється після перезапуску: доки lease чинний, інші сервери лише читають його стан; після завершення lease завдання переходить у `Failed` з позначкою про невідомий результат і без автоматичного replay.
- Черга є DB-authoritative: однаковий `ClientJobId` з тим самим набором параметрів ідемпотентний, інший payload повертає `409 Conflict`, а помилка початкового запису не створює job лише в пам'яті. Replica координують owner/attempt/lease та heartbeat за часом БД, віддалене скасування доходить до власника через БД, а фактичну генерацію між replica серіалізує окремий для кожної БД MySQL named lock. Безпосередньо перед commit виконується DB-fence за owner/attempt/lease/state/cancellation, тому прострочений або віддалено скасований job не може зберегти чернетки. Якщо генератор не реагує на скасування в межах захисного інтервалу, instance припиняє продовжувати lease, записує критичну подію та ініціює зупинку хосту, щоб оркестратор перезапустив процес і закрив DB-session з lock.
- Значення годин модулів у формі є **спільною квотою на всю групу в межах вибраного діапазону**. Для двотижневого запуску значення `8` означає вісім занять на групу за обидва тижні разом, а не по вісім щотижня. Лічильники виконання також агрегують розклад і чернетки за всім діапазоном. Діапазон обробляється календарними тижнями, але всі тижні одного Generate/Fill job виконуються в одній `Serializable`-транзакції: помилка або скасування будь-якого тижня відкочує весь діапазон. Preflight послідовно симулює всі тижні в тій самій транзакції та наприкінці завжди відкочується.
- Hard-rule validator винесений у серверний валідатор і запускається перед збереженням нових чернеток. Він враховує порядок тем від початку навчального періоду, зовнішні чернетки з тими самими викладачами/аудиторіями та сумарну місткість аудиторії на кожному реально пересічному інтервалі.
- Фінальне дозаповнення виконує точний детермінований successive-shortest-path min-cost max-flow: спочатку максимізується кількість заповнених слотів, потім мінімізується вартість і застосовується стабільний лексикографічний tie-break. Поліноміальний solver замінив експоненціальний DFS; план застосовується атомарно й повністю відкочується, якщо будь-яке призначення не проходить hard rules. Один відтворюваний бюджет розгортань вершин діє для групи та дати в межах усього запуску; аварійний тайм-аут лише захищає процес від патологічного зависання.
- Попередження повертаються як структуровані `warningDetails` з кодом, рівнем, категорією, повідомленням і контекстом; старий масив `warnings` збережено для сумісності. Причини незаповнених слотів мають структуровані `reasonCode`, `constraintCode`, ознаку вичерпання пошуку та діагностику. Текстове поле причини збережене для сумісності зі старими журналами.
- Якість алгоритму контролює зафіксована синтетична матриця: короткі профілі та 18-тижневий refill-сценарій на 324 заняття перевіряють KPI, збереження locked-рядків, відсутність `search-limit`, hard-rule порушення, стабільний fingerprint і повторюються тричі в щоденному CI-запуску. Окремий oracle-набір порівнює residual solver з повним перебором на 400 детермінованих малих матрицях і перевіряє стабільність на 512 перемішуваннях входу.

### Локальний двотижневий сценарій L-3

Тест `AutogenL3SeptemberTwoWeekScenarioTests` відтворює робочий сценарій `01.09.2026`–`12.09.2026` для груп `9301`–`9307` із загальними квотами модулів на весь діапазон: `1=8, 2=9, 3=13, 4=10, 5=6, 6=8, 7=6, 8=7, 9=6, 10=7, 11=5, 12=5, 13=3`. Він читає довідники з налаштованої MySQL-бази, копіює їх у тимчасову SQLite-базу й змінює лише цю копію. Сценарій перевіряє первинну генерацію, дозаповнення, обидва тижні діапазону, порядок тем, hard rules, спільні лекції, переходи та повторне ідемпотентне дозаповнення.

```bash
dotnet test BlazorWasmDotNet8AspNetCoreHosted.IntegrationTests/BlazorWasmDotNet8AspNetCoreHosted.IntegrationTests.csproj \
  -p:EnableLocalAutogenHarness=true \
  --filter "FullyQualifiedName~AutogenL3SeptemberTwoWeekScenarioTests"
```

Для запуску має бути доступний `ConnectionStrings:Default` із тих самих джерел конфігурації, що й для сервера. Не додавайте реальні облікові дані до репозиторію.

Приклад локального запуску сервера з HTTP-профілем:

```
dotnet run --project BlazorWasmDotNet8AspNetCoreHosted.Server --launch-profile http
```

Типова адреса з поточних launch settings: `http://localhost:5285`.
