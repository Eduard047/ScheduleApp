# Автогенерація розкладу

Цей документ є єдиним технічним джерелом щодо актуальної автогенерації, job-моделі, сценарію `Plan → Preview → Apply` та контрольних тестів. Короткий користувацький процес описано в [операційному посібнику](../operations-guide.md), а налаштування MySQL і міграцій — у [посібнику з бази даних](../database-setup.md).

## Передумови запуску

- Перед новим семестром у **Адміністрування → Курси** задайте дату початку навчального періоду для кожного курсу. Історія до цієї дати не витрачає години, теми чи баланс навантаження; запуск без дати або раніше за неї відхиляється клієнтом і сервером.
- Автогенерація підтримує тиждень, два або три тижні, місяць і весь курс. Довгі запуски завжди виконуються через job-модель зі збереженим прогресом.
- У production використовуйте налаштований MySQL. SQLite призначений для локальних одно-процесних тестів; через одного writer він не доводить міжпроцесну координацію чи скасування.
- Після оновлення схеми застосуйте всі міграції та переконайтеся, що `GET /health/ready` повертає `200`, перш ніж запускати автогенерацію.

## Job API та життєвий цикл

- Робочий контракт: `POST /api/teacher-drafts/autogen/jobs`. Застарілі синхронні маршрути повертають `410 Gone`.
- Для `Generate` і `Fill` обов'язково передавайте `previewOnly: true`. Спроба прямого запису через job API повертає `400 Bad Request`.
- Стан зберігається в `AutoGenJobRuns`: параметри та hash запиту, owner/attempt, lease, статус, прогрес, результат, звіт, помилка й часові мітки.
- Створення job атомарне та fail-closed. Повторний `ClientJobId` з тим самим hash ідемпотентний; інший payload конфліктує. Помилка запису до БД не створює job лише в пам'яті.
- Черга є DB-authoritative. Owner/attempt/lease з heartbeat за часом БД не дозволяють двом replica виконувати один job; фактичну генерацію між job серіалізує окремий для БД MySQL named lock.
- Один мережевий клієнт може мати не більше двох активних job; HTTP-квота дозволяє до чотирьох запусків за три хвилини. Загальна черга зберігає вісім місць для справедливого обслуговування інших клієнтів.
- Один job має спільний бюджет у 2 000 000 пошукових вузлів і загальний deadline 10 хвилин. Вичерпання будь-якої межі скасовує весь запуск і відкочує його транзакцію.
- Сховище утримує не більше 50 планів, 10 000 mutation-знімків загалом і 2 000 змін в одному плані. Новий preview відхиляється до штатного очищення, якщо квота вичерпана.
- Віддалене скасування спочатку фіксується в БД. Безпосередньо перед commit виконується DB-fence за owner, attempt, lease, state і cancellation, тому прострочений або скасований job не може зберегти чернетки.
- Після аварійного перезапуску незавершений job автоматично не повторюється: після завершення lease він переходить у `Failed` із позначкою про невідомий результат.
- Ownership/lease-міграцію не застосовуйте rolling-способом поверх старих активних генераторів. Припиніть нові job, завершіть або скасуйте активні, зупиніть усі старі instance, створіть резервну копію, застосуйте міграцію й лише потім запускайте нову версію.

## Plan → Preview → Apply

1. `Generate` або `Fill` формує точний незмінний preview-план без зміни робочих чернеток.
2. UI `/admin/schedule` показує точний перелік додавань, змін і видалень. Деталі доступні через `GET /api/teacher-drafts/autogen/jobs/{jobId}/plan`.
3. Окремий `POST .../{jobId}/apply` застосовує план після повторної перевірки його версії, ревізій рядків, релевантної конфігурації та hard rules.
4. `POST .../{jobId}/rollback` відкочує застосований план, якщо створені ним рядки не змінено. Найновіший доступний відкіт повертає `GET /api/teacher-drafts/autogen/plans/latest-rollbackable?courseId={courseId}`.

Preview чинний 24 години. Відкіт доступний 7 днів; після завершення строку дії план видаляється штатним очищенням, щоб сховище залишалося обмеженим. Після перезавантаження UI відновлює авторитетний стан із сервера. Зміна релевантного входу або конфлікт вимагає нового preview.

## Правила планування

- Години модуля — спільна квота однієї групи за весь вибраний діапазон, а не щотижнева квота. Лічильники виконання використовують той самий діапазон.
- Усі тижні одного `Generate`/`Fill` виконуються атомарно. Помилка чи скасування відкочує весь запуск.
- Preflight не записує чернетки: він послідовно симулює весь діапазон в одній транзакції, повертає дефіцити й рекомендації та повністю відкочується.
- Послідовність блоків модулів з `/admin/module-sequence` обов'язкова. Усередині поточного вікна навчального плану календарний порядок тем вільний; генератор не повинен примусово сортувати їх за номером, якщо це створює прогалини.
- Типи занять із прапорцем **«Бажано першим у тижні»** утворюють верхній блок дня. У робочому профілі лекції розміщуються не пізніше 6-ї пари включно, а інші типи — нижче лекційного блока.
- Preflight і фінальне збереження враховують календар, активні слоти, доступні години тем, викладачів, аудиторії, місткість, перетини груп, спільні потоки, корпуси, переходи та модульні блоки.
- Після первинного greedy-планування repair/fill pass дозаповнює прогалини лише в межах hard rules. Перед ним residual solver використовує детермінований successive-shortest-path min-cost max-flow: спочатку максимізує кількість занять, потім мінімізує вартість і застосовує стабільний tie-break.

## Діагностика та якість

- Аналізуйте не лише кількість створених чернеток, а й `warningDetails` (`code`, `severity`, `category`, `message`, `context`) та `gapReasons`: `teacher`, `room`, `travel`, `topic-order`, `module-block`, `limit`, `search-limit`, `shared-flow`, `unknown`, `other`.
- `topic-order` — сумісна назва коду нестачі доступних годин тем, а не вимога календарної черги. Поля `constraintCode`, `searchLimitReached` і `diagnostics` пояснюють фактичне обмеження та бюджет пошуку.
- CI-профіль `AutogenQuality` перевіряє KPI, fingerprints і детермінованість на зафіксованій синтетичній матриці, включно з 18-тижневим refill-сценарієм на 324 заняття. Residual solver звіряється з незалежним brute-force oracle.
- Кожен push і pull request проходить швидку матрицю зі 100 компактних seed-сценаріїв, 24 метаморфних перевірок перестановки/перейменування ID та постійного корпусу regression seeds.
- Нічний `AutogenStress` ділиться на чотири незалежні shards і сумарно запускає 10 000 здійсненних сценаріїв, 2 000 контрольованих дефіцитів, 500 повних lifecycle-циклів і 8 medium/large сценаріїв. Щотижневий soak на восьми shards збільшує межі до 50 000 + 10 000 + 2 000 + 104 відповідно.
- Компактна матриця перебирає лекції, практики, fillers, паралельні блоки та заблоковані чернетки. Scale-профіль окремо покриває до 30 груп, 20 модулів, 18 тижнів, 7 робочих днів і 12 слотів на день, переходи між корпусами, межі місяця/року та високосний лютий.
- Якщо після всіх потокових і атомарних repair-спроб рівно одна група не може приєднатися до вже завершеної спільної лекції, генератор може створити не більше одного окремого лекційного хвоста за запуск. Він проходить ті самі hard rules і не використовується, доки існує партнер для спільного потоку.
- Дефіцитні сценарії не змінюють чернетки й перевіряють відсутність викладача, аудиторії або слотів, відсутність робочих годин викладача, недостатню місткість аудиторій і повністю закритий календар. Lifecycle перевіряє `Preview → stale Apply → Apply → повторний Apply → Rollback` та повторний `Start` з тим самим `ClientJobId`.
- Для кожного збою вказується seed, а CI зберігає TRX-артефакт кожного shard. Повтор діапазонів задається через `AUTOGEN_STRESS_FIRST_SEED`, `AUTOGEN_STRESS_LIFECYCLE_FIRST_SEED` і `AUTOGEN_STRESS_SCALE_FIRST_SEED`; кількість — через `AUTOGEN_STRESS_SCENARIOS`, `AUTOGEN_STRESS_DEFICIT_SCENARIOS`, `AUTOGEN_STRESS_LIFECYCLE_SCENARIOS` та `AUTOGEN_STRESS_SCALE_SCENARIOS`.
- Production guardrails окремо перевіряють lease, idempotency, cancel між двома service instance та серіалізацію MySQL named lock.

Локальний повний синтетичний прогін не підключається до робочої MySQL-бази:

```bash
RUN_AUTOGEN_STRESS=1 \
dotnet test BlazorWasmDotNet8AspNetCoreHosted.IntegrationTests/BlazorWasmDotNet8AspNetCoreHosted.IntegrationTests.csproj \
  --filter "Category=AutogenStress"
```

Приклад точкового повтору з seed `60002`:

```bash
RUN_AUTOGEN_STRESS=1 \
AUTOGEN_STRESS_FIRST_SEED=60002 \
AUTOGEN_STRESS_SCENARIOS=1 \
AUTOGEN_STRESS_DEFICIT_SCENARIOS=0 \
dotnet test BlazorWasmDotNet8AspNetCoreHosted.IntegrationTests/BlazorWasmDotNet8AspNetCoreHosted.IntegrationTests.csproj \
  --filter "FullyQualifiedName~Seeded_synthetic_stress_matrix"
```

У GitHub Actions профілі `quality`, `nightly` і `weekly` також можна запустити вручну через `workflow_dispatch`. Усі синтетичні сценарії використовують окремі тимчасові SQLite-бази; робоче підключення MySQL для них не потрібне.

## Локальний сценарій L-3

`AutogenL3SeptemberTwoWeekScenarioTests` відтворює `01.09.2026`–`12.09.2026`, `Пн–Сб`, для груп `9301`–`9307`. Квоти на групу: `1=7, 2=9, 3=36, 4=10, 5=6, 6=5, 8=7, 10=5, 12=5, 13=3`. Це 93 пари на групу, 651 пара загалом і 252 пари модуля 3.

Тест читає довідники з налаштованої MySQL-бази, копіює їх у тимчасову SQLite-базу та змінює лише копію. Він перевіряє повний цикл `Plan → Preview → Apply`, нуль дефіцитів і пропусків, точні квоти, порядок модульних блоків, вільний порядок тем у поточному вікні, лекційний блок, спільні лекції, hard rules та ідемпотентне дозаповнення.

```bash
dotnet test BlazorWasmDotNet8AspNetCoreHosted.IntegrationTests/BlazorWasmDotNet8AspNetCoreHosted.IntegrationTests.csproj \
  -p:EnableLocalAutogenHarness=true \
  --filter "FullyQualifiedName~AutogenL3SeptemberTwoWeekScenarioTests"
```

Для запуску потрібен `ConnectionStrings:Default` із тих самих джерел конфігурації, що й для сервера. Не додавайте реальні облікові дані до репозиторію.
